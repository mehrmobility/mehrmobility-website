# معماری اجرایی وب‌اپ مشتریان مهر

## تصمیم اصلی

مرورگر مشتری هرگز به دیتابیس یا API خام سامانه داخلی متصل نمی‌شود. مسیر نهایی داده چنین است:

```text
سامانه داخلی مهر
  → Projection عمومی تأییدشده + Transactional Outbox
  → رویدادهای نسخه‌دار Marketplace
  → Customer Read Model مستقل
  → Customer API / BFF
  → وب‌اپ مشتری
```

در مسیر برگشت نیز «درخواست خرید» به Command Outbox پرتال نوشته می‌شود و یک سرویس داخلی مجاز آن را مصرف می‌کند. هیچ دستور مستقیمی از مرورگر وارد هسته داخلی نمی‌شود.

## دلیل نیاز به Projection مستقل

`GET /api/prototype/sales-basket` در سامانه فعلی نزدیک‌ترین منبع طرح فروش است، اما علاوه بر داده مشتری‌پسند، نرخ ارز، منطقه، تعداد دقیق موجودی، کلید طبیعی و شناسه/بازبینی قیمت‌گذاری را هم برمی‌گرداند. بنابراین Proxy مستقیم ممنوع است. ناشر داخلی باید فقط یک DTO سفید‌لیست‌شده تولید کند.

API فعلی قیمت‌گذاری خودروی کارکرده نیز موتور محاسبه قیمت است و «فهرست خودروی تأییدشده برای فروش» نیست. پیش از اتصال واقعی، موجودیت Listing، کارشناسی قابل انتشار و گالری رسانه باید در مرز عمومی ساخته شوند.

## برش اجرایی فعلی روی localhost

برای تحقیق و توسعه محلی، یک Customer Marketplace Read API اختصاصی در سامانه داخلی فعال است:

```text
Browser → Customer BFF :3001 → Customer Marketplace Read API :3000 → D1 محلی
```

این مسیر loopback-only است، درخواست دارای `Origin` را رد می‌کند، توکن مجزای چرخشی دارد و خروجی را با allowlist می‌سازد. حالت لوکال با flag صریح فقط رکوردهای دارای قیمت فروش تأییدشده را به‌عنوان «قابل درخواست تأمین» نشان می‌دهد. این برش جای معماری نهایی Outbox/Read Model را نمی‌گیرد و برای انتشار عمومی مجاز نیست.

## هویت و مالکیت

- مرور کاتالوگ می‌تواند عمومی باشد؛ OTP هنگام ثبت درخواست خرید/رزرو الزامی می‌شود.
- در پنل شخصی، Principal فقط از Session امضاشده و HttpOnly استخراج می‌شود؛ `customer_id` از body/query پذیرفته نمی‌شود.
- دسترسی درخواست خرید، قرارداد، مدارک و ویدئو همیشه با مالکیت رکورد کنترل می‌شود.
- ویدئو و فایل با URL دائمی عمومی عرضه نمی‌شوند؛ Customer API نشست پخش/دانلود کوتاه‌مدت صادر می‌کند.
- OTP، ایجاد درخواست و دریافت رسانه Rate Limit مستقل دارند.
- رضایت مشتری، تغییر وضعیت و تصمیم‌های دسترسی Audit می‌شوند.

## وضعیت‌های مشتری‌پسند

| وضعیت داخلی | وضعیت قابل نمایش |
|---|---|
| Draft / Pending approval | نمایش داده نشود |
| Approved + Published | قابل درخواست |
| Capacity warning | ظرفیت محدود |
| Temporarily held | موقتاً رزرو |
| Sold / Withdrawn / Expired | پایان‌یافته |
| Inspection pending/rejected | نمایش داده نشود |
| Inspection verified + Published | تأییدشده مهر |

## محدوده جاری وب‌اپ

1. فهرست و جست‌وجوی «طرح‌های فروش» و «تأمین خودروی کارکرده»
2. صفحه جزئیات، عکس/ویدئو، قیمت و شرایط قابل انتشار
3. ثبت درخواست خرید یا رزرو پس از OTP و رضایت
4. شماره پیگیری و وضعیت مشتری‌پسند درخواست
5. بارگذاری مدارک در پرونده درخواست
6. اعلان و ارتباط با پشتیبانی همان پرونده
7. پیشنهاد نسخه‌دار، بیعانه، گزارش کارشناسی و پرداخت مانده در Prototype محلی
8. سفر رویدادمحور خودرو از خرید قطعی تا حمل، واردات، ترخیص، PDI و تحویل

پرداخت Prototype هیچ وجهی جابه‌جا نمی‌کند. اتصال واقعی پرداخت، OTP، قرارداد الکترونیکی و رویدادهای زنده فقط پس از تصویب قواعد حقوقی، بازپرداخت، مالکیت خودرو و Customer Read Model انجام می‌شود.
